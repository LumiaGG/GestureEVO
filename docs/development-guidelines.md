# GestureEVO 开发与 PR 审查规范

本文是项目新增代码、修改和 PR 审查的正式依据，适用于所有功能及人工或工具生成的代码。要求覆盖本次改动及其影响的调用路径；既有实现不自动构成例外，也不要求每个 PR 清理无关历史问题。

“必须／禁止／不得”表示合并要求；“优先／建议／默认”表示默认选择，偏离时须在 PR 中说明理由、替代方案和验证证据。其他直接陈述的要求按其适用范围执行。确需偏离合并要求时，由维护者审查具体理由和风险，并在 PR 中记录决定。历史对照与示例用于解释规则，不构成额外的模块专用要求。

本规范随仓库合入生效。验证按改动风险执行，CI 触发及发布策略以[贡献指南](../CONTRIBUTING.md#验证与提交)和现有工作流为准。

## 1. 项目结构与修改边界

- 按 `gesture`、`search`、`inspire`、`drop`、`pin`、`link`、`settings` 等功能组织代码；只有确实跨功能复用的逻辑才进入 `utils`。公共基础设施不得反向依赖具体功能，例如悬浮窗基类不得依赖拖拽包中的注册表。
- Activity、Service、View 负责界面与系统事件协调；规则、解析、几何计算和状态转换等独立逻辑应提取为可测试单元。不得继续向大型界面类或工具类堆入无关职责。
- 复用既有存储、悬浮窗、进程、图标、日志、权限与动作执行入口。多个功能需要同一机制时，提取稳定机制，由功能层保留各自协议和策略；不得为复用少量代码向原业务类添加大量无关模式。
- 新增抽象须解决明确的复用、状态管理或测试问题；不强制为简单功能引入多层 Repository、依赖注入框架或整体架构迁移。
- 一个 PR 聚焦一个问题。行为修改与无关格式化、重命名、依赖升级分开；不得顺带修改无关文件、版本号或发布流程。
- 外部方案按本项目需求移植。额外配套功能、平行执行链或第二套权限后端，须说明需求、既有方案为何不足及维护成本；不得整套照搬上游架构和设置体系。

## 2. 持久化与数据一致性

### 2.1 存储选型

| 数据行为 | 默认方案 | 要求 |
| --- | --- | --- |
| 开关、主题、阈值等少量配置 | 既有 Preferences DataStore | 稳定键名、类型和默认值 |
| 逐条增删改查、筛选、排序、去重、关联或持续增长的记录 | Room | 实体、DAO、约束与迁移 |
| 图片、模型、导出包等大文件 | 文件系统 | 按需持久化元信息，明确所有权与清理策略 |
| 当前会话、加载进度等临时状态 | 内存状态、StateFlow 等 | 明确生命周期，不以持久化充当事件总线 |

按访问与一致性要求选型，不能只看记录数。列表有数量上限也不等于偏好配置，频繁逐条更新的小列表仍可能需要 Room。

### 2.2 DataStore

- 禁止新增将历史、逐条授权或持续增长的业务集合整体序列化为 JSON 写入 DataStore 的实现。少量、有明确规模边界、按整体替换且不需要逐条查询的配置集合可以使用 DataStore，PR 须说明规模、更新频率和理由。
- 兼容维护现有配置格式。既有 JSON 列表不代表新增实现可以照搬；迁往 Room 时须设计迁移，不得直接删除旧键。
- 设置读写复用 `PreferencesManager.kt` 的入口。`settingsStore` 包含 `SettingsSnapshotCache` 封装，禁止绕过封装写底层文件或创建同名 DataStore 实例。
- 读改写必须在同一次 `edit`／`updateData` 中基于最新值完成，不得先读取、修改后再整体覆盖并导致并发更新丢失。更新回调不得夹带网络请求、窗口操作等外部副作用。

### 2.3 Room

- 复用 `DatabaseManager`，在 `db` 中定义实体与 DAO；不得为绕过设计问题随意新建数据库或改用 SharedPreferences。
- 查询绑定参数。筛选、排序、去重、分页优先在 SQL 中完成，避免无必要的整表读取和循环查询。按实际访问设计主键、唯一约束与索引。
- 对查后插入、多记录更新等一致性要求，使用适当事务或数据库约束。冲突策略须符合业务语义，不能无条件照搬 `REPLACE` 并覆盖记录身份或用户字段。
- 禁止主线程阻塞访问、`allowMainThreadQueries()`，或用 `runBlocking` 将异步数据库操作转为主线程同步调用。挂起 DAO 按其异步契约调用，普通阻塞 I/O 使用适当后台执行环境。
- 结构变化同步维护版本、迁移注册及 `app/schemas`；保留已发布 schema，不得改历史 schema 或破坏性重建来绕过用户数据迁移。验证覆盖受支持旧版本的数据、默认值和约束，不能只验证新安装。

### 2.4 权威来源、快照与提交

- 每份数据有明确的权威来源；缓存定义首次加载、更新与失效语义，不得让 UI、缓存和磁盘互相覆盖。用户编辑与偏好不得随可再生索引一起重建。
- 关联配置从同一快照读取并按一致性要求提交。从外部数据源重建索引时，先确认权限、读取成功与完整性，再原子替换有效快照，成功后推进同步标记；增量同步须处理删除。失败不能伪装成成功的空数据。
- 跨 DataStore、数据库、文件和外部系统的操作，明确成功条件、提交点、顺序、重试与补偿。文件落盘后入库失败要回收孤立文件；外部动作失败不能提前标记完成。SQL 事务与进程内 Mutex 均不能代替跨介质的失败恢复。
- 涉及已有多存储协调入口时沿用其约束，例如手势配置写入的 `GestureConfigurationWrites.kt`，不得另建互不协调的写入路径。

## 3. 事件、轮询与执行成本

- 先确定最小工作范围，再选择触发机制。一次交互优先评估一次快照与既有事件；新增刷新须说明失效条件，不得因“事件驱动”而全局监听并持续重扫。
- 有可靠事件源时优先订阅：设置使用 DataStore Flow，窗口变化接入既有无障碍事件与前台跟踪入口，视图就绪使用布局或 attach 回调。需要持续观察 Room 数据时可增加 Flow 查询，不要求一次性查询全部改为订阅。
- 禁止以常驻 `while + delay`、重复 `postDelayed`、Timer 等发现本可订阅的变化；禁止忙等、自旋和无间隔重试。固定延迟不能代替服务、窗口、权限或进程的就绪判断。
- 无可靠事件源或确有系统兼容需要时，可以有限探测。PR 必须交代事件替代方案、激活条件、间隔、总时限或次数上限、成功与失败出口及取消清理；不得扩展为进程常驻扫描。
- 长按计时、超时取消、事件后的单次确认及操作中的帧更新，应有明确取消条件；动画优先使用平台动画或帧回调。心跳、租约等协议机制须说明存活与故障回收语义，不能借此轮询业务状态。
- 可延迟且需要系统调度的任务优先评估 WorkManager；精确提醒按对应系统能力设计。产品承诺必须符合调度能力，不能将尽力调度描述为保证准时。
- 按实际需求初始化权限后端、服务连接、识别与截图。预取须明确时效理由、触发范围和取消路径，不得变为默认全局采集。
- 高频路径不得执行阻塞 I/O、全量同步或重复分配大对象。预览与最终输出分别确定质量，按需采样、加载并限制并发；不得每次绘制重新识别或复制全尺寸图片。
- 缓存、树遍历、字符处理和导入须有容量、生命周期或处理规模边界，并响应取消；截断不能伪装成完整结果。事件去重、防抖与合并不得丢失结束、取消、授权结果等关键事件。

## 4. 异步、资源与生命周期

### 4.1 任务所有者与有效性

- 每个异步任务有明确所有者。界面订阅绑定适当生命周期，Service 和窗口任务随所属组件释放；进程级任务须有理由。禁止 `GlobalScope` 或无人取消的临时作用域。
- 预览与已确认命令可以有不同生命周期。需要在界面关闭后继续的命令，须在明确接收点交给适当上级所有者并传入完整快照；不得因此将预览任务全部提升为服务或进程级任务。
- 重复启动任务时复用、取消旧任务或拒绝重复启动。对不响应取消或延迟完成的操作，发布结果、写回、通知和执行前核对请求、对象或计划版本；旧任务的结果与清理不得覆盖新任务状态。
- 在异步边界固定共同输入，例如文本与坐标、查询与排序条件、源图与尺寸。按需复制可变对象；后台处理中不得反复读取可变全局字段或 View 状态拼接结果。列表回写须核对当前绑定对象。
- 回调或无重放事件转为请求响应时，先监听再触发，匹配请求标识，并处理立即返回、超时、取消与监听释放。
- UI 与 WindowManager 操作在主线程执行；耗时计算和阻塞工作安排到适当后台环境。异常处理、`runCatching` 和通用结果包装必须保留协程取消语义，清理使用可靠路径。

### 4.2 资源所有权与清理

- 接口区分借用、共享与所有权转移。异步消费者须取得有效资源或独立引用，并负责相应释放；沿用 `ManagedBitmap` 等现有机制，不得在借用方销毁共享底层资源。
- Receiver、Observer、监听器、Job、Handler 回调、流、Cursor、Bitmap、文件描述符、进程和 Shizuku 连接明确释放责任，覆盖重复清理、部分初始化失败及中途取消。
- 悬浮窗接入现有 `floating` 管理机制，区分申请、添加、attach、移除与销毁。不得仅根据 `isAttachedToWindow` 推断所有权；复用 `WindowAttachmentRegistry` 等既有竞态处理。
- 外部进程复用现有工具，处理退出码、输出消费、超时和取消回收；不得另建缺少退出路径的执行逻辑。
- 临时资源与用户资产分开管理。清理只覆盖自身受管目录、文件或任务；路径使用规范化后的实际边界校验，不得只比较字符串前缀。延迟清理、取消及重试不得误删永久原件或仍被使用的资源。

## 5. 代码风格与界面一致性

- 遵守 `.editorconfig`：UTF-8、空格缩进，Kotlin 为 4 空格，XML／JSON／YAML 为 2 空格，按文件类型保持换行规则。
- Kotlin 遵循官方风格和相邻维护良好的代码。命名与类型表达业务含义，优先 `val` 和最小可见性；避免无依据的 `!!`、不安全强转、魔法数字和过深嵌套。
- 默认沿用 Views、XML 与 ViewBinding，设置界面复用既有行与卡片组件。引入其他 UI 框架或设计体系须说明必要性与维护方案。
- 文案、颜色、尺寸复用资源与主题；设置变动检查搜索入口，界面变动检查相关深色模式、动态颜色、字体缩放、旋转和窗口边界。
- 主题刷新覆盖附属视图和选中、按下、禁用、描边、轨道等状态，保留组件状态色语义。内容切换或列表复用时重置旧 tint、占位、形状与高亮。
- 注释解释兼容原因、不变量和隐含约束，不逐行翻译代码；删除过时注释和注释掉的实现。公共命名与契约不得仅为风格统一而修改。
- 第三方实现保留来源、版本、版权和许可证，本地适配边界清晰；不为统一风格或消除警告批量修改上游代码。Python 工具、C++ 与发布要求见[贡献指南](../CONTRIBUTING.md#修改范围)。

## 6. 兼容、迁移与系统边界

- 保持配置键、JSON 字段、记录标识、Intent、URI、AIDL 和链接模板等契约。新增字段核对缺失默认值及本地保存、导出、导入；改变行为或格式须给出兼容范围、迁移与失败处理。
- 迁移和恢复先解析、整体校验，再替换有效数据，提交成功前保留可恢复来源。初始化、用户清空与升级迁移分别建模，不能因集合为空重灌默认数据；标记与内容一致提交，重复执行保留用户修改、身份和优先级。
- 新增持久化数据明确是否进入本地／WebDAV 备份。导入校验版本、格式、大小和路径；导出区分可移植配置与本机状态。换设备后重定位文件并验证可用性，不能把持久化 URI 等同于永久访问权，不能直接继承其他设备的授权。
- 新系统能力考虑最低版本、API 差异、权限拒绝与撤回、无障碍断连及 Root／Shizuku 不可用。后台组件只使用已有授权，申请由明确界面操作发起，不得在重连、恢复或查询时自行弹出授权。
- 外部 Intent、URI、文件和 Binder 输入按不可信输入处理，校验来源、目标、范围与临时授权。检查后仍须处理执行时状态变化；不得为单点问题扩大导出或授权范围。
- 数据和动作的保护策略覆盖所有入口及替代路径；主路径拒绝后，不得借另一种采集、解析、导出或执行方式绕过。
- 错误处理保留空结果、取消、拒绝、解析和 I/O 失败的区别，按业务选择提示、重试或保留旧数据。复用 `IoResult` 等既有机制，不得统一伪装为成功或空集合。
- 诊断使用 `AppLogger` 及既有模块，保留必要上下文和失败原因。禁止默认记录完整剪贴板、屏幕文本、联系人、令牌和凭据；高频路径避免逐事件刷日志。

## 7. 数据与行为建模

### 7.1 身份、范围与顺序

- 业务身份独立于名称、文案和列表位置，包含类型、用户／资料空间、来源、子项等必要维度。持久化引用、去重、缓存与异步绑定使用适当稳定身份，不同标识间明确映射。
- 去重、过期、清空、隐藏、置顶和授权明确作用范围；内容相同不等于对象相同，自动处理规则不能无依据地限制手动操作。
- 过滤、用户排序、默认排序、截断和分页的顺序属于行为契约；保持未受影响项的相对顺序。归一化规则在读、写、缓存与删除时一致，不能无条件 `trim()` 或重编码改变已有语义。

### 7.2 状态与恢复

- 区分数据来源、加载状态、用户选择与显示模式。复杂状态使用明确对象与合法转换，不以矛盾布尔值组合承担多个含义；简单功能不强制引入状态机框架。
- 未加载、可请求、已加载为空、失败、拒绝及取消按业务含义区分。`null`、空集合和默认值具有不同语义时，不得用 `orEmpty()` 等处理抹平区别。
- 每个状态字段定义初值、更新者、重置时机和关闭、重进、重建后的行为；初始化和旧异步结果不能覆盖用户刚修改的内容、模式与选择。
- 进程内事件、单例和临时中转不承担可靠恢复，消费方处理缺失。需要恢复的状态使用适当持久化标识或恢复机制，不以一组可变全局字段长期充当会话上下文。

### 7.3 派生数据与共同规则

- 预览、展示、导出和执行复用共同业务规则及数据解释，禁止各自维护不一致的转换。坐标、单位、编码与边界在接口处明确，相关结果作为同一上下文发布。
- 外部结构的正文、标签、元信息与坐标先按语义和优先级解释，再去重合并；不只凭文本相同、控件类名或字符串形状判断含义。

### 7.4 副作用与执行结果

- 查询、解析、预览、绑定和重绘保持可重复，不隐式触发授权、粘贴、发送、执行或历史写入。有意设计的读取修复／清理须明确命名或接口语义与影响范围。
- 预览复用正式执行的本地策略，不为每个候选自动联网探测、解冻或启动；不能本地确定时展示未确定状态。确需联网预览时，明确触发、隐私及取消边界。
- 存储、复制、通知、历史与外部启动分别定义触发条件、顺序和失败行为。某步骤被去重或跳过不代表其他步骤应跳过；某步骤成功也不代表整条操作成功。
- 重复回调、多入口与重试通过幂等键、唯一任务等方式防重，覆盖实际并发范围；防抖或禁用按钮不能代替业务一致性。只重试允许重做且尚未完成的步骤。
- 点击、窗口关闭、拖拽结束、任务入队和 Intent 发起仅代表对应阶段完成。结果与回调表达实际可确认的阶段；取消或失败不得走成功收尾。
- 不同入口复用完整能力判断与执行链，保留用户、来源、目标、触发侧、组件、extras、flags 等必要上下文，以及原有解冻、ROM 适配、定位、诊断与结果处理；不得只借末端参数后绕开既有执行链。

### 7.5 转换、重分发与降级

- 多阶段解析、重定向与重分发有次数／深度上限及循环检测。目标变化后重新校验适用策略，保留最终有效目标与失败阶段。
- 模板中的输入数据不能再次当作语法解释。明确替换顺序、捕获来源、转义和编码，覆盖插入值含占位符、引用缺失及混合语法。
- 区分不支持、有效空结果与策略禁止。仅在能力缺失或执行失败且业务允许时降级；不得把已确认无内容、不可见或被保护的结果重新扩为有效目标。降级保留用户选择及安全边界。

## 8. 验证与 PR 说明

验证遵循[贡献指南](../CONTRIBUTING.md#验证与提交)，按本次影响选择必要检查，不要求每个 PR 完整编译。

| 修改范围 | 验证要求 |
| --- | --- |
| 规则、解析、排序和状态转换 | 行为与边界测试；缺陷修复优先覆盖原复现条件 |
| 持久化、迁移和恢复 | 旧数据、重复执行、并发更新、失败时保留或恢复有效数据 |
| 异步、事件与资源管理 | 取消、立即返回、旧结果晚到、重复启动、销毁后回调与释放 |
| 权限、触摸、进程或系统交互 | 对应边界验证及必要设备记录；注明缺失环境 |
| UI 与公共组件 | 相关主题、布局、状态和交互；核对原有调用方 |
| 文档、低风险样式 | 链接、格式或对应人工检查，不为凑覆盖率新增测试 |

测试验证行为与风险，不复刻实现。按影响覆盖同名不同对象、不同作用范围、空与失败、状态恢复、数据源删除、多步骤部分成功及降级等场景。纯策略或 JVM 测试不能替代所需的系统边界与真机验证。

改动共享入口、系统事件订阅或组件缓存时，核对其他功能的依赖；合并冲突后核对最终组合行为。检查必须对应 PR 最新提交；未执行的验证说明原因和剩余风险，不得描述为已通过。

PR 说明应包含：

- 问题触发条件、修改后行为及影响范围。
- 涉及的存储选型、身份与状态语义、兼容、迁移和备份影响。
- 新增后台任务或探测的必要性、事件替代方案、退出及清理条件。
- 多阶段操作的成功条件、提交点、防重、失败恢复，以及偏离规范的理由。
- 实际执行的检查、结果、设备与未验证范围；新增第三方内容的来源、版本及许可证。

不适用的事项无需扩写。使用[PR 模板](../.github/pull_request_template.md)提交；CI 的自动与手动运行方式仍以贡献指南为准。

## 9. 合并判定

存在以下问题时，应修正后再合并；例外按本文开头的维护者审查规则记录：

- 将业务记录不当存入 DataStore，或以清库、破坏历史 schema 绕过迁移。
- 并发丢更新、过期结果覆盖新状态、多步骤失败后数据或资源无法一致恢复。
- 无依据的常驻扫描、无限重试、主线程阻塞、吞掉取消或任务缺少退出路径。
- 资源提前释放、清理越界、权限或数据保护被替代路径绕过。
- 公共层反向依赖功能、平行体系缺乏必要性，或绕开既有执行链的兼容与保护。
- 身份、策略范围、状态、成功语义或降级处理不明确，导致行为混淆或副作用重复。
- 无关改动扩大范围、大范围偏离既有风格，或缺少与风险相匹配的验证证据。
